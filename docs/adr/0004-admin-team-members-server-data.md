# Administration : rôles dans `team_members`, données lues côté serveur seulement

Le rôle d’équipe d’un compte (`super_admin`, `moderator` ou `viewer`) est stocké dans une table dédiée `public.team_members`, clé primaire `user_id` vers `auth.users` (suppression en cascade), donc au plus un rôle par compte. La table n’a aucun accès client : RLS activée sans aucune policy et `revoke all` pour `anon` et `authenticated`, même pour sa propre ligne. L’espace administration ne charge ses données que par la couche serveur (`server/`), avec le service role : le serveur lit le rôle de l’appelant, puis décide. Le super administrateur est le seul rôle destiné à changer les rôles ; dans le MVP cela se fait en SQL d’exploitation (`docs/admin.md`), une interface viendra plus tard. L’accès n’est jamais accordé d’office selon le domaine d’e-mail.

**Considered options** : colonne de rôle sur `profiles` (rejeté — chaque colonne d’une ligne `profiles` est lisible par son propriétaire (`profiles_select_own`) et, pour un profil public (`is_public` vaut `true` par défaut), par tout le monde (`profiles_select_public`) : la colonne montrerait à tous qui fait partie de l’équipe, et chaque joueur lirait son propre rôle, alors que la table dédiée n’en donne pas même l’accès à sa propre ligne ; côté écriture, la colonne ne serait protégée que tant que les droits de colonne du joueur restent une liste blanche) ; claims personnalisés dans le JWT (rejeté — périmés jusqu’au renouvellement du jeton, et il faut un hook d’authentification pour les poser) ; policy `select` sur sa propre ligne pour l’affichage (rejeté — inutile puisque le serveur lit le rôle ; refuser tout garde la table hors du schéma exposé par l’API pour les joueurs) ; accès automatique selon le domaine d’e-mail (rejeté — un domaine n’est pas une décision d’accès).

**Consequences** : toute lecture ou écriture de `team_members` passe par le service role, donc par du code `server/` ; un nouveau rôle ou un changement de droits se règle côté serveur sans toucher aux droits de la table ; le premier super administrateur et les changements de rôle se font en SQL (`docs/admin.md`) tant qu’aucune interface n’existe ; supprimer un compte supprime son rôle ; quand un écran de gestion des rôles existera, il faudra garder au moins un super administrateur pour que quelqu’un puisse encore gérer les rôles depuis l’application.
