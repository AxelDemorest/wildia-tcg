# Architecture — backend migratable (Nest + Postgres)

Objectif : le front Next reste une coquille UI ; le métier vit dans `server/` et `lib/`. Supabase est un **adaptateur temporaire** (Auth + Postgres + Storage), remplaçable par Nest + Prisma + object storage sans refaire le jeu.

## Couches

| Dossier | Rôle | Futur |
|---------|------|--------|
| `app/`, `components/` | UI, i18n, formulaires | Inchangé |
| `server/actions/` | Transport Next (FormData, `revalidatePath`, `redirect`) | Remplacé par `fetch` vers l’API Nest |
| `server/<domain>/` | Use cases (open pack, grant, queries) | Modules Nest |
| `lib/` | Domaine pur : types, Zod, règles (rareté, farm, tirage) | Package partagé `packages/domain` |
| `lib/supabase/` | Clients Supabase uniquement | Supprimé après migration |
| `supabase/migrations/` | Schéma SQL versionné | Source pour Prisma / migrations Nest |

## Règles obligatoires

1. **Pas de Supabase** dans `app/`, `components/`, ni `lib/` (hors `lib/supabase/`). ESLint bloque ces imports.
2. **Pas de `next/*`** dans `lib/` (hors `lib/supabase/` qui encapsule Next/SSR).
3. **`lib/` n’importe jamais `server/`** — le domaine ne dépend pas du transport.
4. Pages et composants appellent **`server/...`**, jamais `createClient()` Supabase.
5. Auth côté app : type **`SessionUser`** (`lib/auth/session-user.ts`), pas `User` de `@supabase/supabase-js`.
6. Données affichées : types **`lib/cards/types.ts`** (et équivalents), pas la forme brute PostgREST.
7. Métier joueur (inventaire, pièces, boosters) : **uniquement** via `server/` (+ RPC SQL ou service role), jamais depuis le navigateur.
8. **`user_id`** : UUID stable partout ; pas de données métier critiques dans `auth` metadata seule.
9. Images : clé/chemin en base ; URL publique via **`getCardArtPublicUrl`** (demain : base CDN, pas Supabase dans le nom métier).
10. Nouvelle table : migration SQL + mise à jour `docs/security.md` si exposition / RLS.

## Où mettre du code neuf

- Lecture catalogue → `server/cards/queries.ts` (puis repository dédié si le fichier grossit).
- Écriture inventaire → `server/inventory/grant-card.ts` + RPC `grant_card`.
- Ouverture d’un emplacement de la boutique → `openShopSlot` (`server/actions/open-booster.ts`) → `runOpenShopSlot` (`lib/boosters/open-shop-slot.ts`, dépendances injectées) → `openBoosterShopSlot` (`server/boosters/open-pack.ts`) → RPC `open_booster_shop_slot`.
- Chargement d’une ouverture passée par identifiant de tirage → `loadDrawForReveal` (`server/boosters/load-draw.ts`) → `runLoadDraw` (`lib/boosters/load-draw.ts`, dépendances injectées) → lecture de `draw_logs` par le client du joueur (RLS `draw_logs_select_own`, pas de service role).
- Cartes tirées enrichies avec le catalogue pour la révélation → `enrichDrawnCards` (`lib/boosters/enrich-drawn-cards.ts`), appelé par `runLoadDraw` ; `openShopSlot` ne renvoie que le résultat du tirage, la révélation recharge l’ouverture par son identifiant.
- Page de révélation (`app/[locale]/(site)/boosters/opening/[drawId]/page.tsx`) → `loadDrawForReveal` (qui contrôle aussi l’utilisateur : pas de `requireUser` en plus), puis `openingPageAction` (`lib/boosters/opening-page-action.ts`) décide côté serveur de l’issue d’un échec (404, connexion, boutique avec le message `load-failed`), avant que la cérémonie ne lise le repère de la boutique.
- Message de la boutique à la place d’une révélation (`?notice=already-opened` ou `?notice=load-failed`) → `lib/boosters/shop-notice.ts` : `shopNoticeHref` construit l’URL des deux redirections (échec du chargement dans la page de révélation, ouverture déjà effectuée dans la cérémonie) ; la boutique lit le message dans son URL seulement (`useSearchParams` puis `parseShopNotice`) et l’en retire au clic sur un emplacement (`window.history.replaceState`), pour que Précédent ramène à une boutique sans message.
- État de la révélation (paquet au repos, en charge ou qui éclate ; pile, cartes écartées, récapitulatif) → `ceremonyReducer` (`lib/boosters/reveal-ceremony.ts`), avec les durées de la charge et de l’éclat en constantes et `nextPackTimer`, la minuterie de l’étape en cours, que le composant du paquet (`components/boosters/opening-pack.tsx`) pose avec `setTimeout` et dont il passe les durées au CSS ; type du paquet d’une ouverture → `drawPackSlug` (`lib/boosters/booster-pack.ts`) ; repère en mémoire posé par la boutique juste avant de naviguer, lu puis consommé par la cérémonie → `lib/boosters/pending-reveal.ts`.
- Page de l’espace administration (`app/[locale]/(admin)/admin/…/page.tsx`) → d’abord `requireStaff(locale, path)` (`server/auth/require-staff.ts`, avec le chemin de la page sans query string ; un test vérifie que chaque page l’appelle) → `runStaffAccess` (`lib/auth/staff-access.ts`, dépendances injectées) : un visiteur va vers la connexion, un joueur sans rôle d’équipe vers l’accueil du site, un membre équipe reçoit sa session (`StaffSession`, `lib/auth/staff-session.ts`). Le rôle d’équipe est lu dans `team_members` avec le service role, une fois par requête (`cache` de React) ; une lecture en échec (erreur de base, `SUPABASE_SERVICE_ROLE_KEY` absente) est journalisée côté serveur et vaut « pas de rôle » (accueil du site). Le layout admin lit la même session sans rediriger (`getStaffSession`) et ne rend le cadre de l’espace (`components/admin/admin-shell.tsx`, hors en-tête, pied de page, bandeau et chat du site) qu’à un membre équipe : barre latérale fixe dès 1024 px, barre du haut en dessous, nom du membre par `displayLabel` (`lib/profiles/display-label.ts`, partagé avec l’en-tête du site) et `initials` (`lib/profiles/initials.ts`). Les libellés `Admin` sont rendus côté serveur seulement : `app/[locale]/layout.tsx` ne les envoie pas au navigateur ; le titre et le `noindex, nofollow` d’une page admin viennent de son `generateMetadata`, pour un membre équipe seulement (le corps d’une redirection porte aussi les métadonnées) ; chaque page admin le fait en appelant `staffPageMetadata` (`server/auth/staff-metadata.ts`), gardé par `getStaffSession`.
- Accueil de l’espace administration (`app/[locale]/(admin)/admin/page.tsx`) → après `requireStaff`, `loadAdminHome(session)` (`server/admin/home.ts`) → `runAdminHome` (`lib/admin/home-indicators.ts`, compteurs et horloge injectés) : trois comptes lus avec le service role à chaque requête (lignes de `profiles`, lignes de `profiles` créées depuis `now − 7 × 24 h`, lignes de `team_members`), chacun dans son `number | null` : un compte en échec est journalisé côté serveur et ne vide que son indicateur (tiret et « Indisponible » pour les lecteurs d’écran). `formatIndicator` écrit le nombre pour la locale avec `formatCount` (`lib/admin/format-count.ts`, que le registre réutilise). Cartes : `components/admin/admin-kpi-card.tsx` et `admin-role-badge.tsx` (libellés reçus en props, jamais de `useTranslations("Admin…")` côté client) ; couleurs des pastilles de rôle dans le thème Tailwind (`admin-moderator`, `admin-moderator-soft`, `admin-neutral-soft`).
- Registre des comptes inscrits (`app/[locale]/(admin)/admin/accounts/page.tsx`) → après `requireStaff`, la recherche et la page viennent de l’URL (`?q=`, `?page=`) par `parseSearchTerm` et `parsePage` (`lib/admin/accounts-query.ts` : recherche nettoyée et coupée à 100 caractères, page invalide → 1) → `listAccounts(session, { search, page })` (`server/admin/list-accounts.ts`) → `runListAccounts` (`lib/admin/list-accounts.ts`, lecture injectée) → RPC `admin_list_accounts` (service role ; `profiles` joint à `auth.users`, du plus récent au plus ancien, 50 par page, avec le total de la recherche et, par compte, `balance` = somme de `currency_ledger.amount`, 0 sans mouvement, par un seul agrégat pour la page ; migration `20261125140000_admin_list_accounts_balance.sql`). `runListAccounts` décide depuis la session qui voit et cherche les e-mails et le dit dans son résultat (`emailsMasked`, sur une page comme sur un échec : la page en tire le libellé de la recherche et l’indication « E-mails masqués pour votre rôle »), masque ceux d’un lecteur (`maskEmail`, `lib/admin/mask-email.ts`) et renvoie la page, une redirection vers la dernière page quand la page demandée la dépasse (la page la fait avec `redirect`, recherche gardée), ou un échec (journalisé par `server/`, message dans la carte du tableau, sans nombre de comptes). Pages et liens : `accountsPagination` et `accountsPageQuery` (`lib/admin/accounts-pagination.ts`). Libellés reçus en props, jamais de `useTranslations("Admin…")` côté client : `components/admin/accounts-search.tsx` (composant client, formulaire GET `next/form` ; quand la recherche ou la page de l’URL change, le champ reprend la recherche de l’URL sans être remonté, le focus clavier reste en place), puis les composants serveur `accounts-table.tsx` (colonne du nom fixe quand le tableau défile, une ligne « aucun compte » pour une recherche vide), `accounts-pagination.tsx` (liens `Link` qui gardent la recherche, pied de page du téléphone sur une ligne). Dates écrites côté serveur, à l’heure de Paris : `formatAdminDate` et `formatAdminDateTime` (`lib/admin/admin-dates.ts`) ; nombres par `formatCount`. Ajout de pièces, pour le super administrateur seul (`GRANT_COINS_ROLE`, `lib/admin/grant-coins.ts` : la page n’ajoute la dernière colonne du tableau que pour lui) : `GrantCoinsButton` (`components/admin/grant-coins-button.tsx`, composant client : bouton de la ligne à icône seule, boîte `AdminDialog`, `useActionState`, champs contrôlés, « Ajouter » désactivé pendant l’envoi) → `grantCoins` (`server/actions/admin-coins.ts`) → `runGrantCoins` (`lib/admin/grant-coins.ts` : session relue, rôle, identifiant de compte au format UUID, montant par `wholeNumberIn` de `lib/admin/whole-number.ts`, motif nettoyé, refus par champ signalés ensemble ; une écriture en échec devient `unknown_account` ou `failed`, sans page d’erreur ; `refresh` injecté, appelé après une écriture réussie par `writeThenRefresh`, comme les autres écritures de l’espace administration) → `writeCoinGrant` (`server/admin/coins.ts`, échec journalisé, sauf le refus `unknown_account`, relancé tel quel) → RPC `admin_grant_coins` (ligne d’`admin_coin_grants` et ligne `admin_adjust` du journal dans une transaction ; compte sans profil → exception `unknown_account`). Le rafraîchissement suit un ajout réussi (la colonne « Solde » de la ligne montre le nouveau solde) ; le succès s’écrit dans une notification (`AdminNotifications`, `components/admin/admin-notifications.tsx`, monté une fois par `AdminShell` ; `useAdminNotify` ; texte de la ligne écrit par la page avec `GRANTED_AMOUNT_PLACEHOLDER` à la place du montant, que le navigateur remplace par `formatCount`), pas dans la ligne. Le courriel, la cellule la plus large, passe à la ligne dès 1024 px quand le tableau a la colonne du bouton, pour que le tableau ne déborde pas à 1280 px.
- Paramètres du jeu (`app/[locale]/(admin)/admin/settings/page.tsx`) → `requireStaff(locale, path, SETTINGS_ROLE)` (troisième paramètre `role` : un membre équipe d’un autre rôle est renvoyé vers l’accueil admin ; `SETTINGS_ROLE` = `super_admin`, `lib/admin/setting-values.ts`) → `loadSettings(session)` (`server/admin/settings.ts`) → `runLoadSettings` (`lib/admin/settings-page.ts`, lectures injectées ; `forbidden` sans rien lire pour un autre rôle, la page redirige alors comme la garde ; `failed` si une lecture échoue, message à la place des cartes et de l’historique) : valeurs d’`economy_config`, 20 dernières lignes d’`admin_setting_changes` de ces paramètres puis noms affichés de leurs auteurs dans `profiles`, le tout avec le service role. Enregistrer : `SettingCard` (`components/admin/setting-card.tsx`, composant client, `useActionState`, champ contrôlé qui reprend la valeur du serveur quand elle change, sans être remonté) → `saveSetting` (`server/actions/admin-settings.ts`) → `runSaveSetting` (`lib/admin/save-setting.ts` : session relue, rôle, clé connue, bornes de `parseSettingValue` dans `lib/admin/setting-values.ts`) → `writeSetting` (`server/admin/settings.ts`) → RPC `admin_set_economy_config` (valeur et ligne d’historique dans une transaction) → `refresh()` (`next/cache`), qui rend la page de nouveau dans la réponse de l’action. Restaurer : `RestoreSettingButton` (`components/admin/restore-setting-button.tsx`, boîte `AdminDialog` de `components/admin/admin-dialog.tsx` : `<dialog>` natif ouvert par `showModal()`, formulaire neuf à chaque ouverture, fermé dans la transition de l’action pour apparaître avec l’historique à jour) → `restoreSetting` → `runRestoreSetting` (`lib/admin/restore-setting.ts` : identifiant de ligne seulement, `readChange` relit le paramètre et sa valeur « Avant », mêmes bornes qu’une saisie) → `writeSetting` avec `restoredFrom`. L’historique (`components/admin/settings-history.tsx`, composant serveur) écrit dates et nombres pour la locale et passe à chaque bouton ses libellés et le texte de sa boîte en props. Boosters de la même page : `loadSettings` lit aussi toutes les définitions de booster (`boosterFromRow`, `lib/admin/booster-values.ts`). Enregistrer une carte : `BoosterSettingsCard` (`components/admin/booster-settings-card.tsx`, composant client : interrupteur « Actif » et champs contrôlés, envoyés ensemble) → `saveBooster` → `runSaveBooster` (`lib/admin/save-booster.ts` : session, rôle, toute la carte par `parseBoosterCard`) → `writeBooster` → RPC `admin_set_booster_definition` (une ligne d’historique par valeur changée ; les règles « au moins un booster disponible » et « au moins une chance positive » y sont vérifiées sous verrou de la table, et un refus lève une exception dont le message est son code, que `writeThenRefresh` rend par `boosterRuleOf` au lieu de `failed`). Une ligne de booster se restaure seule (`boosterChange`), après les mêmes bornes (`parseBoosterValue`). Total et parts des chances, part des emplacements : `lib/admin/booster-shares.ts`, calculés par la page sur les valeurs enregistrées ; nom d’un booster dans l’espace administration, son slug à défaut de message : `boosterName` (`lib/admin/booster-name.ts`).
- Retour après connexion (`/{locale}/login?returnTo=…`) → `safeReturnTo` (`lib/auth/return-to.ts`) : la page de connexion lit `returnTo`, ne garde qu’un chemin interne (sinon `/{locale}`), redirige un compte déjà connecté vers lui et le passe au formulaire (`AuthForm`, champ caché) ; `signIn` le contrôle de nouveau avant de rediriger. `signIn`, `signUp` et `signOut` passent la locale reçue du navigateur par `knownLocaleOrDefault` (même fichier) avant de construire une redirection ou un `revalidatePath` ; `signUp` l’envoie aussi dans les métadonnées du compte (`options.data.locale`), d’où `handle_new_user` tire `profiles.locale`. `loginHref(locale, returnTo)` (même fichier) construit ce lien de connexion (locale contrôlée, chemin encodé) pour `requireUser(locale, path)` (page ou action réservée aux joueurs connectés, chemin sans query string), `requireStaff`, et la page de révélation. Le lien de connexion de la boutique boosters utilise le `Link` de next-intl avec `{ pathname, query }` (pas `loginHref`, pour éviter `/fr/fr/login`).
- Inscription par e-mail (`signUp`, `server/actions/auth.ts`) → `runEmailSignUp` (`lib/auth/email-sign-up.ts`, dépendances injectées) : limite par IP, origine de la requête, limite par adresse, suppression du compte non confirmé de l’adresse (`delete_unconfirmed_account` par le service role), puis `supabase.auth.signUp` avec `emailRedirectTo` = `emailConfirmUrl` (`lib/auth/callback-url.ts` : `{origine}/{locale}/auth/confirm?returnTo=<assaini>`). Le formulaire est remplacé par l’état `check_email` (`role="status"`, adresse tapée) et le bouton « Renvoyer le lien » (`components/resend-confirmation-form.tsx`, action `resendConfirmation` → `runResendConfirmation`). Le lien du mail (`token_hash` ajouté par le modèle) arrive sur `app/[locale]/auth/confirm/route.ts` → `completeEmailConfirm` (`server/auth/email-confirm.ts` : `verifyOtp({ token_hash, type: "signup" })` avec le client serveur, qui pose les cookies de session) → `runEmailConfirm` (`lib/auth/email-confirm.ts`, vérification et journal injectés) : redirection vers `safeReturnTo(returnTo)` ; un lien utilisé, expiré ou inconnu (`otp_expired`) mène à `/{locale}/login?error=link_expired`, toute autre erreur ou un lien sans `token_hash` à `error=failed` (`failureUrl`), `returnTo` gardé. La route n’écrit pas `profiles.locale`. Le mail est en français ou en anglais (`supabase/templates/confirmation.html`, branche sur `.Data.locale`). Si Supabase renvoie une session (« Confirm email » désactivé), l’action redirige vers `returnTo`.
- Connexion avec Google ou Discord (`components/oauth-sign-in-form.tsx`, formulaire client à son propre `useActionState`, champ caché `returnTo`, un bouton par fournisseur : `name="provider"`, `value="google"` ou `"discord"`, icônes de `components/ui/brand-icons.tsx`, boutons désactivés ensemble pendant un départ) → `signInWithProvider(sentLocale, prev, formData)` (`server/actions/auth.ts`) → `runOAuthStart` (`lib/auth/oauth-start.ts`, origine et construction de l’URL d’autorisation injectées ; le fournisseur vient du navigateur et doit être dans `OAUTH_PROVIDERS`, sinon `failed` sans URL) : l’URL de retour est `{origine}/{locale}/auth/callback`, avec `?returnTo=` quand `safeReturnTo` garde un chemin autre que l’accueil ; l’origine vient de `x-forwarded-proto` et `x-forwarded-host`, à défaut de `host` (`originFromHeaders`, `lib/auth/request-origin.ts`) ; l’action appelle `signInWithOAuth` du client SSR (PKCE, le vérificateur reste dans un cookie) puis redirige vers l’URL d’autorisation. Le retour arrive sur `app/[locale]/auth/callback/route.ts` → `completeOAuthSignIn` (`server/auth/oauth-callback.ts` : `exchangeCodeForSession`, puis écriture de `profiles.locale` avec le service role) → `runOAuthCallback` (`lib/auth/oauth-callback.ts`, échange et écriture injectés) : la locale de l’URL n’est écrite que pour un compte créé par cette connexion (`last_sign_in_at − created_at` dans la durée de vie du code d’authentification, 5 min), puis redirection vers `safeReturnTo(returnTo)` ; une écriture de locale qui échoue est journalisée sans bloquer la connexion. Un refus ou une erreur (`error` / `error_code` / `error_description` de l’URL, `oauthErrorCode`, `lib/auth/oauth-error.ts` : un e-mail non fourni par Discord ou non vérifié → `email_unusable`, une identité refusée par la base → `account_refused`), un code manquant ou un échange refusé renvoient vers `/{locale}/login?error=<access_denied|email_unusable|account_refused|link_expired|failed>` (`returnTo` gardé ; `link_expired` ne vient pas du callback mais de la route `/auth/confirm`) : la connexion lit `?error=` par `parseOAuthError` et affiche le message `Auth.oauthError.*` (neutre, sans nom de fournisseur) ; l’inscription l’ignore. Le départ compare d’abord le fournisseur à `OAUTH_PROVIDERS`, puis passe par `assertAuthRateLimit` (`auth:{ip}`) : refusé, le message `Auth.errorRateLimited` s’affiche sur le formulaire OAuth ; un départ qui échoue montre `Auth.oauthError.failed`, comme un retour en échec. Les deux pages sont composées par `components/auth-card.tsx` (OAuth, séparateur, formulaire e-mail de `AuthForm`, lien vers l’autre page avec `returnTo` par le `Link` de next-intl) ; `signUp` relit `returnTo` avec `safeReturnTo` et la page d’inscription renvoie un visiteur connecté vers lui, comme la connexion. Un déclencheur de base (`private.guard_provider_identity`, migration `oauth_identity_guard`) refuse les identités OAuth non vérifiées ou liées à un compte e-mail confirmé sans clic (`docs/security.md`).
- Validation entrée → Zod dans `lib/` quand c’est réutilisable, sinon en tête de l’action.
- Logique pure testable → `lib/` + test Vitest.

## Server Actions

Traitées comme **glue Next** : validation → `getUser()` / `requireUser()` → appel `server/<domain>/` → effets cache Next. La logique métier ne doit pas vivre dans `server/actions/` au-delà de l’orchestration.

## Migration Nest (rappel)

- Conserver les **mêmes UUID** utilisateurs et le schéma `public.*`.
- Remplacer `lib/supabase` par Prisma + auth Nest ; réimplémenter les mêmes fonctions exportées de `server/`.
- Les RPC SQL peuvent être appelées depuis Nest au début, puis portées en TS transactionnel si besoin.
